## Why proposing and regenerating don't block each other

| Layer | Command | Costs | Redo when | Proposals that affect it |
|---|---|---|---|---|
| 1. Collect replies | `run` / `fill` | the tested models' APIs | scenario wording changes (hash) | wording edits |
| 2. LLM judge | `judge` / `fill` | the judge's API | `RUBRIC_VERSION` bump | added highlights, rubric changes |
| 3. Score + export | `rejudge`, `report`, `export_web` | nothing (local) | any time | scoring rules, removed highlights, licensing |

Most span proposals only touch layers 2–3, so collected replies stay valid.
`fill` treats a version bump or a rewording as new gaps: bump the rubric and
the next `fill` re-judges; reword a scenario and it collects that scenario
again. Old rows are never touched.

## Using `fill`

```bash
.venv/bin/projectionbench fill --dry-run            # what's missing, what's resting; no requests
.venv/bin/projectionbench fill                      # work until everything left is resting
.venv/bin/projectionbench fill --watch --hours 8    # wait out cooldowns and keep going
```

What it does:

- **Compares the DB with `fill.yaml`** instead of queueing a fixed batch. A
  conversation counts only if every probe is error-free at the current wording.
- **Round-robins across quota scopes** (API key + model), so one slow provider
  doesn't starve the others. A judge and a subject on the same key (DeepSeek on
  NVIDIA is both) share one scope.
- **Classifies errors from real messages in your DB:**
  - 429 per-minute: rest for the provider's retry hint, then doubling.
  - Daily quota: rest 1h, doubling to 6h. Per model for Gemini; the whole key
    for OpenRouter's and Cloudflare's account-wide caps.
  - 503 / overloaded: rest 30s, doubling to 30 min; never counts against the
    task (the first real run hit Gemini "high demand" 503s at 4am).
  - Timeout / dropped connection: rest 30s, doubling to 10 min; a task that
    times out 3 times waits for the next `fill`.
  - 401/404: park that subject for the session, since waiting won't fix config.
  - Cooldowns live in the DB, so tomorrow's run respects tonight's daily limit.
- **Never substitutes models.** A throttled subject waits; another model
  answering would be different data. The judge is pinned; a second judge in
  `fill.yaml` adds a column rather than filling the first one's gaps.
- **Saves every reply as it arrives** and continues an interrupted conversation
  from its last stored reply (only within 36h, because model aliases drift).
- **Gives new conversations fresh sample numbers** (after the highest stored),
  so keys don't collide again.
- **Re-exports `web/src/lib/data.json`** every 20 new rows and when it stops.
- **Known limitation:** requests run one at a time, so a slow provider pauses
  every key. At 04:33 an NVIDIA DeepSeek subject request hit its 150s timeout
  and everything else waited. Nothing is lost, it's just slower. One worker per
  quota scope is the obvious next improvement; I didn't build it tonight.
  Separately, a conversation that times out 3 times in one `fill` waits for the
  next `fill`, so a very slow model may need a couple of runs.
